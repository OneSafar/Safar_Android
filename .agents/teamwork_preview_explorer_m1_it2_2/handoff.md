## 2. Logic Chain

1. **SQLite Primary Key Collation Behavior (Observation 1.1 §1, 1.2 §1, 1.2 §2)**:
   - In SQLite, the primary key constraint generates an automatic unique index (`sqlite_autoindex_<table>_<n>`).
   - By default, text columns have `BINARY` collation sequence.
   - When a primary key is declared on a column without explicit collation, its index uses `BINARY` collation.
   - Under `BINARY` collation, ASCII byte comparison determines equality. `"@Veritasium"` (ASCII 'V' = 86) and `"@veritasium"` (ASCII 'v' = 118) compare as not equal.
   - Therefore, SQLite treats `"@Veritasium"` and `"@veritasium"` as two distinct records.

2. **Defect in Unnormalized Inserts & Policy Shadowing (Observation 1.1 §2, 1.1 §4, 1.2 §1)**:
   - When `YouTubeChannelRepositoryImpl.normalizeHandle` preserved casing, consecutive saves with different casing produced two distinct primary keys in SQLite.
   - `INSERT OR REPLACE` failed to detect a primary key collision.
   - When `YouTubeChannelDao.getPolicyByHandle` queried `WHERE channelHandle = :handle COLLATE NOCASE LIMIT 1`, SQLite returned the first matching row encountered in table-scan order (the older `PRODUCTIVE` classification), permanently shadowing the user's newer `DISTRACTING` classification.

3. **Storage-Layer Resolution via `collate = ColumnInfo.NOCASE` (Observation 1.1 §1, 1.2 §2, 1.2 §3, 1.2 §4)**:
   - Specifying `collate = ColumnInfo.NOCASE` on `@ColumnInfo(name = "channelHandle")` causes Room's schema generator to emit `channelHandle TEXT NOT NULL COLLATE NOCASE`.
   - SQLite builds `sqlite_autoindex_youtube_channels_1` with collation sequence `NOCASE`.
   - Consequently, SQLite's conflict resolution for `INSERT OR REPLACE` considers `"@Veritasium"` and `"@veritasium"` identical.
   - Any insertion with differing casing replaces the existing row in-place, guaranteeing single-row uniqueness and eliminating stale policy shadowing at the database engine level.

4. **Application-Layer Resolution via `.lowercase()` Normalization (Observation 1.1 §2, 1.1 §5)**:
   - Adding `withAt.lowercase()` in `YouTubeChannelRepositoryImpl.normalizeHandle` guarantees that all repository operations (`saveChannelPolicy`, `getChannelPolicy`, `getChannel`, `deleteChannel`) normalize handles to canonical lowercase before touching Room or memory structures.
   - This ensures that in-memory collections (such as Kotlin `Map` or `Set` which use standard case-sensitive string equality) and UI Flow emissions (`getAllChannels`) remain strictly consistent.
   - It also directly aligns production repository logic with the existing `E2EInMemoryChannelRepository` in `YouTubeGuardE2ETest.kt`.

5. **Defense-in-Depth Guarantee**:
   - The database layer (`collate = ColumnInfo.NOCASE`) protects against direct SQL / DAO operations, raw queries, or fallback handle casing variations.
   - The repository layer (`.lowercase()`) guarantees canonical data flow throughout Kotlin coroutines, state flows, and UI state models.
   - Together, both changes guarantee that `INSERT OR REPLACE` properly overwrites records regardless of casing variations, preventing policy shadowing.
