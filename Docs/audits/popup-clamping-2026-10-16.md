## Why the screen and pop-ups differ

The screen theme in [SafarTheme.kt](/Users/shashankkumar/Documents/SAFAR_PARENT/Safar_Android_v5/app/src/main/java/com/safarparmar/app/ui/theme/SafarTheme.kt:130) sets a custom display density (`min(heightPx/820, systemDensity, widthPx/360) × 0.85`) and bounds font scale to **1.0–1.45**. [MainActivity.kt](/Users/shashankkumar/Documents/SAFAR_PARENT/Safar_Android_v5/app/src/main/java/com/safarparmar/app/MainActivity.kt:162) also narrows the app content to a portrait-shaped region on landscape tablets.

Dialogs, menus, and modal sheets create a separate Android Compose view. In the resolved library source, that view initializes density from its Android context, and `ProvideCommonCompositionLocals` provides `owner.density` again. This shadows the parent theme’s density. Passing the parent composition context preserves many theme values but does not preserve this overridden `LocalDensity`. The app must capture and restore it inside the new content to keep the same scale. The popup window also does not automatically inherit MainActivity’s narrow tablet content bounds.

Inspected resolved versions: Compose UI **1.11.4**, Material 3 **1.4.0**, Composables UI **0.2.0**, Compose Unstyled **2.7.0**. Dependency source files were inspected locally; this conclusion is not based just on a text search for `widthIn`.

Local source evidence: AndroidComposeView initializes `Density(context)`; `CompositionLocals.kt` provides `LocalDensity` from the owner; Android Dialog/Popup and Material ModalBottomSheet create a new view. Unstyled’s Android modal uses `ComponentDialog` plus `ComposeView`. No ModalHost is installed in the app to take its alternate in-tree path.
